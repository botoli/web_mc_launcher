# Minecraft Launcher

Веб-панель и кабинет игроков на **Next.js / React / TypeScript** с backend на **Express**.

## Запуск

Production-размещение на сервере, Nginx, права служб и IP-сертификат: [docs/deployment.md](docs/deployment.md).

Для веб-приложения и бота используется Node.js 24 LTS; для базы нужен PostgreSQL 16+. Параметры подключения, схема, перенос прежних данных и резервирование описаны в [docs/database.md](docs/database.md). Перед первым запуском перенесите существующие JSON-данные командой `npm run db:migrate`, затем `npm run db:verify`.

```powershell
cd E:\mc_launcher\web_mc_launcher
npm.cmd install
npm.cmd run dev
```

Откройте **http://localhost:3000**. Для Windows PowerShell используется `npm.cmd`, чтобы запуск не зависел от политики выполнения `.ps1`.

Для production:

```powershell
npm.cmd run build
npm.cmd start
```

Обе команды запуска (`dev` и `start`) поднимают Express и отдельный процесс Next.js. Остановка через Ctrl+C завершает оба процесса. `npm.cmd run start:backend` запускает только Express; без Next.js страницы будут недоступны, API продолжит работать.

## Настройки и архитектура

Можно скопировать `.env.example` в `.env` и изменить настройки. Общий скрипт запуска загружает `.env` из корня проекта. Переменные окружения процесса имеют приоритет.

- **Express** принимает публичные запросы на `PORT` (по умолчанию `3000`).
- `/api/*`, `/mods/*` и `/download/*` обслуживает существующий backend.
- Страницы и `/_next/*` Express проксирует в Next.js на `127.0.0.1:FRONTEND_PORT` (по умолчанию `3001`). WebSocket-проксирование поддерживает обновление интерфейса при разработке.
- Заходить в приложение нужно через **порт Express**, а не через внутренний порт Next.js.
- Next.js получает данные для серверного рендеринга непосредственно от Express. Cookie авторизации передаётся только в backend; JWT не хранится в localStorage.

`HOST` задаёт адрес Express (по умолчанию `127.0.0.1`); Next.js также слушает только loopback. При прямом доступе к dev-серверу с другого компьютера задайте `HOST=0.0.0.0` явно.

`PUBLIC_URL` задаёт внешний HTTP(S)-адрес без пути. Если он не указан, адрес вычисляется из `DOMAIN`, `PORT` и прежнего `USE_HTTPS`. HTTPS в публичном адресе включает `Secure` для cookie независимо от внутреннего транспорта.

За Nginx задайте `PUBLIC_URL=https://<адрес>`, `HTTPS_ENABLED=false` и `TRUST_PROXY=loopback`. Proxy должен передавать `X-Forwarded-Proto` и заменять клиентский `X-Forwarded-For`. `HTTPS_ENABLED=false` отключает встроенный TLS, даже если в `data/certs` остались файлы. Без явного отключения встроенный TLS запускается при наличии `privkey.pem` и `fullchain.pem`, на `HOST:HTTPS_PORT` (по умолчанию `127.0.0.1:3443`).

Приложения сгруппированы в `apps/`. Зависимости и npm-команды остаются общими в корне репозитория. Пути к `.env` и `data/` вычисляются от корня через `apps/api/src/config/paths.js` и не зависят от текущего каталога терминала:

```text
apps/
  api/src/
    server.js             Express API, авторизация, файлы и proxy в Next.js
    auth/                 Хеширование и проверка паролей
    config/               Пути к конфигурации и данным
    database/             PostgreSQL, транзакции, schema.sql
    players/              Профили, роли, модерация и журнал
    telegram/             Серверные сценарии авторизации и кабинета бота
  web/
    app/                  Страницы и layout Next.js
    components/           React-компоненты интерфейса
    lib/                  Типы и клиенты API
  bot/                    Независимый Telegram worker без npm-зависимостей
scripts/
  run.js                  Совместный запуск веб-приложения и API
  db/                     Перенос прежних JSON и резервирование PostgreSQL
tests/                    Тесты API, бота, базы и браузерные сценарии
deploy/                   Systemd-службы
docs/                     Архитектура, PostgreSQL, контракт лаунчера
data/                     Моды, клиенты, сертификаты, исходные JSON, резервные копии
bot/                      Прежняя точка запуска и существующие приватные настройки
server.js                 Прежняя точка запуска API
frontend                  Ссылка на apps/web для совместимости прежних путей
```

Где вносить изменения и как обновлять существующую установку: [docs/architecture.md](docs/architecture.md). Команды `npm run dev`, `npm run build`, `npm start`, `npm run start:backend`, `npm run start:bot` и `npm run db:*` выполняются из корня репозитория.

Существующие launcher API, JWT, форматы ответов конфигурации и паролей сохранены; пользователи, настройки, журнал и состояние Telegram хранятся в PostgreSQL. Новый защищённый `GET /api/dashboard` выдаёт исходные данные панели без паролей и токенов. Административные действия и доступ к логам требуют роли; система ролей описана ниже.

## Интерфейс

- `/` — настройки сборки, Java, памяти и игрового сервера.
- `/mods` — «Моди и конфиги»: отдельные блоки модов и ZIP-архива конфигов, загрузка, замена и скачивание. Конфиги включаются в архив сборки под `configs/`; [контракт синхронизации для лаунчера](docs/launcher-configs.md).
- `/players` — поиск игроков, статусы и карточка действий.
- `/logs` — общий журнал действий игроков.
- `/profile` — данные аккаунта и изменение никнейма.
- `/login`, `/register` — вход и регистрация.

Цвета: `#AC88F6`, `#1A1A1A`, `#464646`, `#222222`, `#B8FEBF`. Шрифт Manrope поставляется локально вместе с приложением. В интерфейсе есть адаптивная навигация, состояния загрузки, сообщения об ошибках и клавиатурное управление.

На широком экране страницы помещаются в высоту окна; на узком длинные формы и списки прокручиваются внутри области содержимого без прокрутки всей страницы и без выхода за ширину экрана.

## Проверки

Telegram-авторизация лаунчера: [запуск отдельного бота, настройки и API](apps/bot/README.md). Бот регистрирует игроков с паролем, привязывает существующие аккаунты после проверки пароля и предоставляет личный кабинет с редактированием профиля и управлением сессиями. Вход начинается с ручного ввода кода из лаунчера; вход запрещён при бане и действующей заморозке. [Контракт для лаунчера](docs/launcher-auth.md).

```powershell
npm.cmd run typecheck
npm.cmd run build
npx.cmd playwright install chromium --only-shell
npm.cmd test
```

Тесты запускают Next.js и Express на свободных локальных портах, создают отдельные временные данные и проверяют API и действия в браузере. Настоящая папка `data` не используется. PostgreSQL-тесты создают отдельные схемы `mc_test_*`; отдельное подключение можно задать через `TEST_DATABASE_URL`. Скриншоты сохраняются в `artifacts/`.

## Логи, действия игроков и роли

- `/players` → ник игрока или **«Действия»** → вкладки **«Данные об игроке»**, **«Лог авторизаций»**, **«Подключения на сервер»**, **«Все действия»**.
- `/logs` — общий журнал: таблица с отдельными колонками времени, игрока, Telegram/Discord-юзернейма, действия, источника, IP и результата; поиск по текущему или прежнему нику, логину, юзернейму, IP, боту и деталям; фильтры по типу, источнику, результату и датам, страницы по 30 записей. Время и границы дат — Москва (UTC+3).

Две роли: **админ** и **игрок**. Существующий аккаунт с точным логином `botoli1` автоматически имеет роль админа и единолично управляет выдачей ролей. Его роль закреплена. Логины и другие данные существующих аккаунтов не меняются.

Войдите как `botoli1`, откройте `/players` и выберите **«Админ»** или **«Игрок»** в колонке **«Роль»**. Выданные роли сохраняются в таблице PostgreSQL `users`; изменение прав действует сразу, в том числе для уже открытых сессий. Другие админы видят роли без возможности их менять. Новые аккаунты получают роль игрока; регистрация и редактирование профиля не позволяют повысить права. Роль определяется по стабильному логину, а не по игровому нику. Списки ролей через `ADMIN_LOGINS` / `SUPPORT_LOGINS` больше не используются.

Админ управляет сборкой, модами, игроками, логами и ограничениями лаунчера. Игрок имеет доступ к своему профилю. Каждое изменение роли записывается в журнал с инициатором `botoli1`, предыдущей и новой ролью. В API допустимы только `admin` и `player`.

Дополнительные настройки интеграций:

```dotenv
# Необязательно, только при работе за доверенным reverse proxy:
TRUST_PROXY=loopback
# Отдельный случайный секрет от 32 символов для событий Minecraft/Discord:
PLAYER_EVENTS_SECRET=replace-with-a-long-random-service-secret
```

Бан и временная заморозка действуют **только в лаунчере**, в том числе на Telegram-сессии и `/api/verify`. Вход на сайт и собственный профиль доступны. Бан и заморозка отзывают ранее выданные launcher-сессии навсегда; после разбана, снятия или истечения заморозки нужно войти в лаунчер заново. Заморозка ограничена 8760 часами, допускает дробное число часов и проверяется по серверному времени при каждом запросе. Снятие ограничения не требует таймера или перезапуска. Эти операции не выдают Minecraft-бан и не отключают уже запущенный игровой клиент от игрового сервера.

Таблица PostgreSQL `player_events` пополняется при регистрации, успешном/неуспешном входе через сайт или лаунчер, выходе, смене ника, Telegram-привязке/отвязке и входе через бота, модерации, изменении ролей, добавлении/замене/удалении модов и изменении конфигурации сборки. Запись содержит время, стабильный логин, ник и Telegram/Discord-юзернейм на момент события, ID платформы, IP (когда известен), источник, способ, бота, результат и инициатора. Действия ещё не привязанных Telegram-пользователей записываются по их ID и юзернейму. Секретные поля, тело запроса и текст сообщений не сохраняются. При неизвестном IP Telegram/Discord он остаётся пустым; IP хоста бота не выдаётся за IP игрока. Для реального IP за proxy настройте `TRUST_PROXY` только на доверенный proxy. Пароли, JWT, коды входа и секреты в журнал не записываются. Старые события до внедрения логирования восстановить нельзя.

Журнал переживает перезапуск и входит в общий дамп PostgreSQL: `npm run db:backup`. Изменения аккаунтов, настроек, журнала и Telegram фиксируются транзакционно; блокировка PostgreSQL защищает записи между процессами. Старые JSON-файлы остаются резервным источником на момент переноса и больше не обновляются.

### Подключение событий Minecraft и Discord

Для логов подключений используется защищённый API игрового сервера; для будущего Discord-бота — API входа и привязки ниже. Внутренние действия клиента лаунчера не собираются; исходники лаунчера для этого журнала не нужны. Вход в лаунчер не считается фактическим подключением к Minecraft-серверу.

Оба API принимают `Content-Type: application/json` и заголовок `X-Events-Secret: <PLAYER_EVENTS_SECRET>` только от доверенного серверного интегратора. Не размещайте этот секрет в лаунчере или браузерном JS.

`POST /api/internal/server-events`:

```json
{
  "login": "player_login",
  "action": "connect",
  "ip": "203.0.113.10",
  "server": "play.example.com:25565"
}
```

Действия: `connect`, `disconnect`, `connection_denied`; необязательный `reason` поясняет отказ/отключение. Вместо `login` допустим `nickname`: регистр не учитывается, при совпадении нескольких аккаунтов нужен стабильный логин. IP обязателен и проверяется как IPv4/IPv6. Время — время получения события сервером панели.

`POST /api/internal/discord-events`:

```json
{
  "login": "player_login",
  "action": "discord_linked",
  "discordId": "123456789012345678",
  "username": "player.discord",
  "bot": "MyDiscordBot",
  "ip": ""
}
```

Действия: `discord_linked`, `discord_unlinked`, `login`, `logout`. `username` передаёт отображаемое имя. Необязательное `destination` указывает, куда выполнен вход: `discord`, `launcher` или `website`; по умолчанию `discord`. Привязка сохраняет Discord ID в карточке игрока; вход/выход и отвязка требуют совпадения с существующей привязкой. Повторное использование одного Discord ID другим аккаунтом отклоняется. Пустой IP означает, что бот не знает адрес игрока. Этот API регистрирует подтверждённые ботом события; OAuth/новый механизм входа через Discord он не создаёт.

Основные защищённые API панели:

```text
GET  /api/admin/players/:login
GET  /api/admin/players/:login/actions
GET  /api/admin/logs?login=&q=&category=&source=&outcome=&from=&to=&page=&limit=
POST /api/admin/players/:login/moderation  {action: ban|unban|freeze|unfreeze, reason?, hours?}
PUT  /api/admin/players/:login/role       {role: admin|player} — только botoli1
```

Для `ban` и `freeze` обязательна причина. Секретные интеграционные API не принимают пользовательский JWT вместо сервисного секрета. Логи и IP доступны только админам и не включаются в публичный `/api/users`.


### Какие события записываются

- Входы и выходы на сайте и в лаунчере, входы через Telegram/Discord, отказы авторизации, отзыв сессий. Для входа указываются источник, назначение, время, IP (когда известен), ID платформы, юзернейм и бот.
- Фактические подключения к игровому серверу и отключения — по событиям серверной интеграции.
- Регистрация, смена данных аккаунта, привязка/отвязка Telegram и Discord.
- Изменения администратора: бан/разбан, заморозка, статусы, роли; добавление/замена/удаление модов; изменение конфигурации сборки. Указываются инициатор и объект изменения. Неизменённая конфигурация повторно не логируется.

Просмотры страниц, чтение профилей и списков, открытие журнала, HTTP-запросы сами по себе, команды/клики ботов, служебная очистка сообщений и внутренние действия клиента лаунчера не записываются. API телеметрии клиента удалён. Старые технические события больше не отображаются и не входят в счётчики/страницы, при этом исторический файл журнала сохраняется.

В Telegram остаются регистрация с паролем, смена ника/email/пароля, отзыв сессий и очистка сообщений. Бот редактирует один текущий экран и удаляет предыдущие сообщения; история действий доступна только в веб-панели админам. Смена пароля завершает все web- и launcher-сессии; `botoli1` остаётся единственным управляющим ролями. Подробнее — [инструкция бота](apps/bot/README.md).
