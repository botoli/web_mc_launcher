# Telegram: регистрация и личный кабинет Equestrian Dream

Бот запускается отдельным Node.js worker. Единственный процесс, который изменяет пользователей, сессии и логи — Express backend. Worker получает обновления Telegram, передаёт их backend по HTTPS и выполняет разрешённые команды ответа/удаления. База пользователей на хост бота не копируется.

## Запуск и обновление

1. На сервере нужны `apps/api/`, `apps/web/`, `scripts/`, корневые `package.json`, `package-lock.json`, `.env`, `data/` и установленные зависимости проекта. Для сайта выполните из корня `npm run build`, затем `npm start`.
2. Укажите `TELEGRAM_BOT_SECRET` длиной от 32 символов в серверном `.env`.
3. На хосте бота нужен Node.js 22+. Скопируйте папку `apps/bot/`, создайте в скопированной папке `.env` (образец — [`.env.example`](.env.example)):

   ```dotenv
   telegrambotapi=<токен BotFather>
   AUTH_API_URL=https://ваш-домен
   TELEGRAM_BOT_SECRET=<тот же общий секрет, что на backend>
   ```

4. Запустите `node bot.js` внутри скопированной папки или `npm run start:bot` из корня полного репозитория. Worker не требует npm-зависимостей. Используйте один экземпляр и менеджер процессов для автоматического перезапуска.

В существующей установке корневая папка `bot/` сохраняет приватные настройки: если `bot/.env` существует, worker использует его и `bot/.delivery-receipts.json`. Иначе используются файлы рядом с `apps/bot/bot.js`. Прежняя команда `node bot/bot.js` продолжает работать. При переносе настроек в `apps/bot/` остановите worker и переместите `.env` вместе с `.delivery-receipts.json`, если он существует; старый `.env` имеет приоритет. Переменные окружения процесса имеют приоритет над `.env`, а `TELEGRAM_DELIVERY_STATE_FILE` задаёт явный путь к подтверждениям доставки.

При обновлении нужно перезапустить **backend и worker**: старый worker не поддерживает редактирование текущего сообщения и новые подтверждения доставки. Имя бота определяется через `getMe`. Бот не меняет существующий webhook: при его наличии или конфликте long polling запуск завершается с понятной ошибкой. HTTP разрешён только для localhost при разработке; рабочее соединение требует HTTPS.

## Регистрация и привязка

`/register` или «Регистрация» → свободный Minecraft-ник → пароль → повтор пароля → подтверждение кнопкой → личный кабинет.

Ник: 3–16 латинских букв, цифр или `_`. Пароль: 8–128 символов, допускаются пробелы; без перевода строки. Логин создаётся как `tg_<Telegram ID>`, при коллизии добавляется суффикс; он отображается в кабинете. Пароль работает на сайте и в парольном API лаунчера. Новый аккаунт имеет статус `pending` и роль `player`. Существующие логины не меняются.

`/link` → существующий игровой ник → **пароль этого аккаунта** → подтверждение. Поиск ника не учитывает регистр. Привязка сохраняет логин, пароль и остальные данные. Перед подтверждением заново проверяются пароль, занятость ника, статус и привязка Telegram. Для ввода текущего пароля допускается 5 попыток в минуту на Telegram ID; лимит сохраняется при перезапуске.

Если у старого непривязанного аккаунта нет пароля, требуется восстановление через администратора. У уже привязанного аккаунта без пароля его можно задать в кабинете. Один Telegram ID может быть связан только с одним аккаунтом. Авторизация опирается на постоянный ID; `@username` используется для отображения и истории, не для выдачи прав.

## Личный кабинет

`/account` показывает логин, ник, email, Telegram-юзернейм и ID, Discord, роль, статус, активную заморозку и причину, дату регистрации, последний вход, число Telegram-сессий и наличие пароля.

Кнопки кабинета:

- **Никнейм** — проверка формата и уникальности, сохранение нового ника.
- **Email** — сохранение корректного адреса; `-` удаляет email.
- **Пароль** (`/password`) — текущий пароль, новый пароль, повтор. Если пароль раньше не задавался, достаточно действующей Telegram-привязки. Смена пароля завершает все launcher- и web-сессии; доступ к боту сохраняется по Telegram ID.
- **Сессии** (`/sessions`) — активные Telegram-сессии и сроки; подтверждаемое завершение всех сессий лаунчера, включая JWT-входы.
- **Отвязать** — подтверждение, сохранение аккаунта, отзыв launcher-сессий и отмена незавершённых запросов. Перед отвязкой должен быть задан пароль. Для заблокированных аккаунтов отвязка недоступна.
- **Войти в лаунчер** — ручной ввод кода с экрана лаунчера.

`/menu` возвращает в кабинет/главное меню. `/cancel` отменяет текущий сценарий. Просмотр кабинета и помощи не отменяет незавершённый ввод; начало другого изменения его заменяет. Изменения профиля доступны при ограничениях лаунчера, а выдача игровой сессии проверяет бан и заморозку.

## Одно активное сообщение

Бот работает одним экраном: меню, кабинет, формы и подтверждения редактируют текущее сообщение через `editMessageText`. В одном обновлении формируется один ответ, поэтому успешное сохранение и данные кабинета показываются вместе. Кнопки и команда истории действий отсутствуют; пользователь не получает доступ к журналу через Telegram.

Все входящие сообщения пользователя, включая команды, никнейм, email и пароли, удаляются после обновления экрана. Известные старые ответы бота также удаляются. Текущий экран исключён из очереди удаления. Worker подтверждает успешную отправку или редактирование, после чего сразу выполняет очистку.

Если пользователь вручную удалил экран и Telegram отклонил редактирование, worker отправляет новое сообщение, сохраняет его ID и очищает предыдущие сообщения. Повторное открытие уже показанного экрана (`message is not modified`) считается успешным обновлением и не создаёт дубль. ID текущего экрана и очередь очистки сохраняются в backend и переживают перезапуск. Worker сохраняет неподтверждённые ID экранов в `.delivery-receipts.json` рядом с выбранным `.env`: после сбоя связи или перезапуска сначала подтверждается уже доставленное сообщение, затем обрабатываются новые обновления. Файл содержит только тип подтверждения и числовые ID, без текста сообщений и паролей. Каталог бота должен быть доступен для записи; другой путь можно задать через `TELEGRAM_DELIVERY_STATE_FILE`.

В состоянии хранятся ID и время, без текста сообщений и открытых паролей. Удаление выполняется пакетами до 100 ID через `deleteMessages`; при сбое worker пишет диагностику, а очередь повторяет попытку через 30 секунд. При переходе со старой версии первый ответ очищает известные прежние сообщения.

Telegram разрешает удалять обычные сообщения младше 48 часов. Бот не может получить ID всей старой истории до внедрения учёта, а недоступные для удаления сообщения могут потребовать ручного удаления. Эти ограничения определяет [Telegram Bot API](https://core.telegram.org/bots/api#deletemessage). В учёте хранятся последние 5000 известных ID на чат за 48 часов.

## Логирование и хранение

Журнал получает входы/выходы, неуспешные проверки пароля, регистрацию, привязку/отвязку, изменения профиля, смену Telegram-юзернейма и завершение сессий. Команды, кнопки, просмотры кабинета, шаги диалогов и служебное удаление сообщений в пользовательский журнал не записываются. У каждого события есть Telegram ID, текущий на момент события `telegramUsername` и имя бота. Пароль, код входа, параметры deep link, тексты переписки и токены не записываются. Для отказа авторизации сохраняются только факт и причина отказа.

Непривязанные пользователи тоже видны в журнале по Telegram ID/юзернейму. После регистрации новые события связываются со стабильным логином. Telegram не передаёт IP пользователя боту; для чатовых действий IP остаётся пустым. При обмене кода на сессию фиксируется IP запроса лаунчера.

Новые пароли хешируются `scrypt` с солью. Старые PBKDF2/SHA256/bcrypt-пароли проверяются совместимым модулем; парольный вход обновляет хеш. Пароли нельзя восстановить из кабинета.

Таблицы PostgreSQL `telegram_*` содержат хеши секретов/сессий, диалоги с хешами паролей во время подтверждения, лимиты, очередь удаления, ID текущего экрана и известных сообщений, а также offset. Они резервируются вместе с пользователями и журналом командой `npm run db:backup` в корне backend. Дампы нельзя публиковать или включать в лаунчер. Старые JSON-файлы сохранены только как источник переноса. [Настройка базы](../../docs/database.md).

## Контракт и проверки

[API для разработчика лаунчера](../../docs/launcher-auth.md), включая шаг `awaiting_password` и состав данных журнала входов.

Внутренние маршруты требуют `X-Bot-Secret`:

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/internal/telegram/connect` | Имя бота, offset |
| POST | `/api/internal/telegram/update` | Обработка update; только личные сообщения |
| POST | `/api/internal/telegram/pending-actions` | Повтор удаления сообщений |
| POST | `/api/internal/telegram/delivery` | ID отправленного/отредактированного экрана, результат удаления |

`npm run test:telegram` проверяет регистрацию, кабинет, секретность и удаление без реального Telegram. `npm test` также проверяет API сайта и браузерный интерфейс. Для живого запуска нужны настроенные `.env`, HTTPS и бот BotFather.
