# Конфиги сборки

На странице `/mods` («Моды и конфиги») администратор загружает один ZIP-архив до 500 МБ. Он может содержать файлы и вложенные каталоги непосредственно в корне либо внутри одной папки `config/` или `configs/`. Общая внешняя папка убирается; в скачиваемом архиве файлы всегда лежат под `configs/`. Вложенные каталоги сохраняются. Поддерживаются до 10 000 записей и до 1 ГБ после распаковки.

Новая загрузка полностью заменяет опубликованный набор. Сервер сначала проверяет все пути, размеры и контрольные суммы и распаковывает архив во временную ревизию; только успешная загрузка публикуется. Повреждённые, пустые и зашифрованные архивы, ссылки, выход за пределы каталога и повторяющиеся пути отклоняются. Текущие скачивания завершаются со своей прежней ревизией. Файлы и метаданные хранятся в `data/configs/`, отдельно от модов; новая схема БД не нужна.

## API панели

- `POST /api/upload-configs` — multipart-поле `configs`, один `.zip`; нужна роль администратора. Ответ: `{ success: true, configs: { name, size, unpackedSize, fileCount, hash, updatedAt } }`. Размеры указаны в байтах, время — Unix time в миллисекундах.
- `GET /api/configs-info` — администратору возвращает `{ configs: <метаданные или null> }`. Те же данные входят в `/api/dashboard`.
- `GET /api/download-configs` — публичный ZIP с папкой `configs/` в корне. До первой загрузки возвращает `404`.

Успешные загрузка и замена фиксируются в журнале как `configs_added` и `configs_replaced`. Ошибка валидации возвращает `400`, превышение размера загружаемого файла — `413`.

## Синхронизация в лаунчере

Существующий `GET /api/download-mods` теперь отдаёт архив следующей структуры:

```text
mods/
  example.jar
configs/
  example.toml
  nested/options.json
```

`modsURL` в `/api/client-config` сохраняется. `modsHash` учитывает также SHA-256 содержимого конфигов: даже изменение файла без изменения его размера запускает повторное скачивание сборки. Пока конфиги не загружены, прежний расчёт хеша модов сохраняется.

Дополнительные поля `/api/client-config`:

```json
{
  "configsHash": "<SHA-256 содержимого конфигов или empty>",
  "configsURL": "http://<сервер>/api/download-configs",
  "configsDirectory": "configs"
}
```

До первой загрузки `configsURL` равен `null`.

Лаунчер должен распаковывать весь архив `modsURL` **в корень конкретной сборки**, сохраняя относительные пути. Тогда конфиги окажутся в `<сборка>/configs/`, рядом с `<сборка>/mods/`. Если клиент переносит из архива только `.jar` или только папку `mods/`, его нужно изменить: исходников клиента в этом репозитории нет.

При отдельной синхронизации конфигов сравнивайте `configsHash`, скачивайте `configsURL` и распаковывайте архив также в корень сборки: папка `configs/` уже включена в ZIP. Сохраните хеш только после успешного скачивания и распаковки. Не распаковывайте архив непосредственно в `configs/`, иначе получится `configs/configs/`.

Для обновления без смешивания ревизий сначала распакуйте новый набор во временный каталог, проверьте, что пути остаются внутри сборки, затем замените управляемые сервером файлы. Сервер заменяет набор целиком; удаление устаревших локальных файлов и сохранение пользовательских настроек зависят от реализации клиента.
