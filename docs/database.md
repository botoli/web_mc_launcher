# PostgreSQL

Backend использует PostgreSQL через `pg`. Express продолжает обслуживать API, Next.js — интерфейс. `apps/api/src/server.js` и общий runner читают `.env` из корня проекта; переменные окружения процесса имеют приоритет. Адаптер базы и SQL-схема находятся в `apps/api/src/database/`, команды обслуживания — в `scripts/db/`. Отсутствие подключения останавливает запуск: автоматического переключения на JSON нет.

## Подключение

На текущем сервере база — `mc_launcher`, пользователь — `mc_launcher`, адрес — `127.0.0.1:5432`, схема — `public`. Пароль находится в `PGPASSWORD` корневого `.env`. Пользователь приложения владеет своей базой и не имеет прав суперпользователя. PostgreSQL слушает локальные адреса.

Параметры перечислены в [`.env.example`](../.env.example). Можно использовать `DATABASE_URL` вместо отдельных `PG*`; пароль в URL должен быть URL-encoded. Для удалённой базы с TLS настройте параметры SSL в строке подключения, включая проверку сертификата.

Для DBeaver/DataGrip с другого компьютера настройте SSH-туннель к серверу, а адрес PostgreSQL внутри туннеля — `127.0.0.1:5432`. Вариант через терминал:

```sh
ssh -N -L 15432:127.0.0.1:5432 root@87.58.220.248
```

После этого подключайтесь с компьютера к `127.0.0.1:15432`, указывая базу, пользователя и пароль выше.

## Таблицы

| Таблица | Назначение |
| --- | --- |
| `users` | Логин, пароль в исходном формате, профиль, роль, статус, версии сессий |
| `user_identities` | Telegram/Discord ID и юзернеймы, связь с аккаунтом, уникальность ID |
| `user_moderation` | Заморозка, причина, статус до бана, связь с аккаунтом |
| `application_settings` | Настройки сборки, игрового сервера, версии клиента и метаданные бота |
| `player_events` | Полный журнал в исходном порядке, включая прежние скрытые технические события |
| `telegram_challenges` | Запросы входа и подтверждения |
| `telegram_sessions` | Сессии лаунчера с хешами токенов |
| `telegram_conversations` | Незавершённые диалоги |
| `telegram_code_attempts` | Ограничения ввода кода |
| `telegram_password_attempts` | Ограничения проверки пароля |
| `telegram_profiles` | Профили пользователей Telegram |
| `telegram_messages` | Известные сообщения и время |
| `telegram_active_messages` | Текущий экран каждого чата |
| `telegram_deletions` | Очередь удаления сообщений |
| `schema_migrations` | Версия схемы, отметка импорта, контрольные суммы и путь к резервной копии |

Схема находится в [`apps/api/src/database/schema.sql`](../apps/api/src/database/schema.sql). JSONB внутри отдельных сущностей сохраняет дополнительные старые поля, различия между `null` и отсутствующим полем, числовыми/строковыми ID, а также объектами/строками старых паролей. Индексируемые столбцы автоматически вычисляются из JSONB, поэтому данные не расходятся. Для изменения таких полей SQL-клиентом меняйте соответствующий ключ `data`, например `data = jsonb_set(data, '{nickname}', '"NewNickname"')`; вычисляемый `nickname` обновится автоматически.

Внешние ключи связывают привязки и модерацию с `users.login`. Журнал и старые Telegram-записи сохраняют логины удалённых/неизвестных аккаунтов без удаления истории. Неуникальные игровые ники разрешены для совместимости; Telegram/Discord ID уникальны. Исторические события с одинаковым `id` сохраняются отдельными строками с последовательным номером.

## Перенос

1. Установите PostgreSQL 16+ и создайте отдельную базу с пользователем. Заполните `.env`, установите зависимости через `npm ci`.
2. Остановите прежний backend и бота, чтобы JSON не менялся во время импорта.
3. Выполните `npm run db:migrate`, затем `npm run db:verify` до запуска приложения.
4. Выполните `npm run build` и запустите приложение и бота.

По умолчанию импортируется `data`. Для другого каталога: `npm run db:migrate -- /absolute/path/to/data`. Переносятся `users.json`, три конфигурации, `telegram-auth-state.json` и все строки `player-events.jsonl`. Файлы модов, клиентов, сертификаты и очередь подтверждений доставки удалённого worker остаются файлами.

Импорт создаёт приватную копию исходных файлов с SHA-256 в `data/backups/pre-postgres-*`, проверяет точное совпадение данных внутри транзакции и только затем фиксирует её. Ошибка формата, конфликт ID или изменение источника отменяют импорт. Повторный запуск возвращает сведения о выполненном импорте и не заменяет данные работающей базы. Импорт в уже заполненную базу без отметки миграции запрещён.

Если первый импорт делался до остановки старых служб, после их остановки допустим `npm run db:migrate -- --refresh-before-cutover`. Он обновит импорт только при условии, что PostgreSQL всё ещё полностью совпадает с предыдущей резервной копией. После появления новых данных в PostgreSQL этот режим откажет в обновлении, чтобы не затереть их. `db:verify` сравнивает базу с JSON на момент переноса; после начала обычной работы их расхождение ожидаемо.

## Транзакции и проверки

Каждый API-запрос получает своё состояние из PostgreSQL; изменения пользователя, бота, настроек и журнала фиксируются одной транзакцией перед ответом. Ошибка сохранения возвращает 503 без успешного ответа и авторизационной cookie. Блокировка PostgreSQL координирует запросы и импорт между процессами, защищая от потери изменений и повторного обмена Telegram-кода. Страницы и файловые скачивания освобождают транзакцию перед передачей ответа, чтобы серверный рендеринг мог обращаться к API.

Для совместимости с текущей синхронной логикой API обрабатываются последовательно под блокировкой и загружают состояние приложения, включая журнал, в память запроса. При значительном росте журнала следующим шагом будет перенос его фильтрации и пагинации непосредственно в SQL. Текущая схема содержит индексы по логину, времени и категории.

`npm test` использует отдельные случайные схемы `mc_test_*` и временные каталоги, затем удаляет их. Можно выделить отдельную тестовую базу через `TEST_DATABASE_URL`; по умолчанию используется настроенное подключение с отдельными схемами. `npm run test:database` проверяет перенос, идемпотентность, откат, конкурирующие процессы и постоянные Telegram-сессии. Telegram unit-тесты отдельно проверяют прежний файловый адаптер модулей; рабочий сервер всегда передаёт PostgreSQL-адаптер.

## Резервирование

`npm run db:backup` создаёт приватный PostgreSQL custom dump в `data/backups/*.dump`. Для команды нужен `pg_dump` версии не ниже версии сервера. Включайте дампы, `data/mods`, `data/clients`, сертификаты, `.env` и выбранные настройки и подтверждения доставки бота (`bot/.env` и `bot/.delivery-receipts.json` для существующей установки либо файлы в `apps/bot/`) в резервирование. После переноса старые JSON сохраняются для истории и больше не обновляются рабочим сервером.

Восстановление дампа проверяется в отдельной пустой базе командой `pg_restore --no-owner --exit-on-error --dbname=<отдельная_база> <путь_к_dump>` с параметрами доступа через окружение. Для отката приложения после начала работы на PostgreSQL сначала остановите записи и экспортируйте актуальные данные; старые JSON уже не содержат новых изменений.
