# Запуск и перенос через Docker

На целевом сервере нужны только Docker Engine и плагин `docker compose`. Node.js, PostgreSQL, systemd-службы приложения и ручная установка Nginx не требуются. Для Ubuntu установка Docker описана в [официальной инструкции](https://docs.docker.com/engine/install/ubuntu/). Все команды ниже запускаются из корня проекта либо распакованного установщика.

## Готовый установщик

Установочный архив `mc-launcher-docker.tar.gz` содержит подготовленный образ приложения и образы PostgreSQL/Caddy, Compose и скрипты управления. Он не содержит рабочих данных и секретов. Для Linux с той же архитектурой:

```sh
tar -xzf mc-launcher-docker.tar.gz
cd mc-launcher
./install.sh http://NEW_IP:8080
```

Откройте `http://NEW_IP:8080`. Это новая пустая установка. Для HTTPS укажите `https://launcher.example.com`: DNS домена должен вести на новый сервер, порты 80/443 должны быть доступны. Caddy получит и будет продлевать сертификат автоматически. Старые IP-сертификаты текущего сервера переносить не требуется. HTTP предназначен для локальной проверки; для работы с паролями используйте HTTPS.

Для **переноса текущих аккаунтов, модов, конфигов и состояния бота** передайте вторым аргументом свежий архив данных:

```sh
./install.sh https://launcher.example.com /path/to/migration.tar.gz
```

Скрипт восстановит базу и файлы, сохранит секреты авторизации, сменит публичный адрес и запустит сайт. При восстановлении существующая конфигурация и непустая база не перезаписываются. Восстановление выполняется в чистую установку до запуска API. Пароли PostgreSQL в новом стеке отдельные от текущего сервера. Архив данных и `.env.docker` приватные: они содержат токен бота и секреты, поэтому не публикуйте их.

## Однократный экспорт из текущей установки systemd

На старом сервере, в существующем каталоге проекта:

```sh
export PATH=/opt/mc-launcher/runtime/node/bin:$PATH
cd /opt/mc-launcher/web_mc_launcher
sudo systemctl stop mc-launcher-bot mc-launcher-server
node scripts/docker/export-host.js /root/migration.tar.gz https://launcher.example.com
```

Экспорт откажется работать при активных службах, чтобы база и файлы соответствовали одному моменту. В архив входят логический дамп PostgreSQL, `data/mods`, `data/clients`, `data/configs`, выбранные секреты сервера, токен и актуальные подтверждения доставки бота. Исторические JSON, старые дампы и сертификаты остаются на старом сервере; актуальные аккаунты и Telegram-диалоги уже находятся в PostgreSQL.

Перенесите `migration.tar.gz` и установщик на новый сервер и выполните команду с архивом выше. Время экспорта и копирования — окно остановки записи. Если переезд отменяется, запустите прежние службы командой `sudo systemctl start mc-launcher-server mc-launcher-bot`. После начала работы новой базы не возвращайтесь к старому снимку без переноса новых изменений.

## Telegram-бот

Восстановление по умолчанию оставляет бот выключенным. Когда прежний worker остановлен, задайте в `.env.docker`:

```dotenv
COMPOSE_PROFILES=bot
```

Токен уже будет перенесён из старой установки. Для новой установки заполните также `TELEGRAM_BOT_TOKEN`. Затем:

```sh
./scripts/docker.sh up -d --wait
```

Backend и worker получают один общий `TELEGRAM_BOT_SECRET`. Worker обращается к backend по loopback внутри общей сетевой среды контейнеров, поэтому не зависит от внешнего DNS и сертификата. Не запускайте два worker с одним токеном одновременно.

## Запуск из исходников

```sh
./scripts/docker/init.sh https://launcher.example.com
./scripts/docker.sh up -d --build --wait
```

Первый скрипт создаёт `.env.docker` с отдельными случайными паролями и секретами; существующие `.env` и `bot/.env` он не изменяет. Повторный запуск сохраняет конфигурацию. Изменение только адреса с сохранением секретов:

```sh
./scripts/docker/init.sh https://new-domain.example --update-url
./scripts/docker.sh up -d --wait
```

При запуске контейнера сохранённый `launcherServer` сборки также обновляется на `PUBLIC_URL`, чтобы восстановленная база не отправляла пользователей на прежний сервер.

Сервисы: `app` (Next.js и Express, Node.js 24), `db` (PostgreSQL 16), `proxy` (Caddy), необязательный `bot`. `tools` запускается только для обслуживания. API работает от непривилегированного пользователя `node`; пользователь базы приложения не суперпользователь. PostgreSQL и внутренний API не публикуют порты хоста. Внешние порты по умолчанию 8080/443 для HTTP-примера и 80/443 при выборе HTTPS. Если эти порты заняты другой установкой, меняйте `HTTP_BIND`, `HTTP_PORT`, `TLS_PORT` в `.env.docker`.

База, рабочие файлы, очередь бота, сертификаты и кеш находятся в отдельных Docker volumes. `docker compose down` сохраняет их; **`down -v` удаляет тома с данными**. `restart: unless-stopped` поднимает сервисы после перезапуска Docker. Проверки готовности ожидают PostgreSQL и сайт перед запуском зависимых сервисов.

## Резервные копии Docker и перенос между Docker-серверами

```sh
./scripts/docker/backup.sh /root/migration.tar.gz
```

Скрипт кратковременно останавливает API и worker, делает дамп и копию файлов, добавляет `.env.docker` и SHA-256, затем запускает ранее работавшие API/worker. На момент окончательного переключения отдельно остановите прежний стек: `./scripts/docker.sh stop bot app proxy`. Новая установка восстанавливается через `install.sh URL ARCHIVE` либо из исходников:

```sh
./scripts/docker/restore.sh /path/to/migration.tar.gz https://new-domain.example
./scripts/docker.sh up -d --build --wait
```

Восстановление проверяет SHA-256, отсутствие таблиц и рабочих файлов. Бот включается отдельно после остановки прежнего экземпляра. Сертификаты Caddy выпускаются заново, кеш Next.js пересоздаётся.

Полезные команды:

```sh
./scripts/docker.sh ps
./scripts/docker.sh logs --tail=100 app bot
./scripts/docker.sh restart app
./scripts/docker.sh down
```

Для подключения SQL-клиента через терминал:

```sh
./scripts/docker.sh exec db sh -c 'psql -U "$APP_DB_USER" -d "$APP_DB_NAME"'
```

## Собрать переносимый установщик

В полном исходном проекте, после создания `.env.docker`:

```sh
./scripts/docker/package.sh /root/mc-launcher-docker.tar.gz
```

Архив содержит образы для архитектуры машины сборки. Для другого типа процессора соберите проект на целевой архитектуре или подготовьте multi-platform образы отдельно. Образы не публикуются в registry, секреты и пользовательские данные в Docker build context исключены через `.dockerignore`.
